Modular Composition

How we build big things so many helpers can work at the same time and never bump into each other. Like Lego.

1. The big idea: one brick, one box, one helper

Think of a pile of Lego. Every kind of brick lives in its own box. In a program, a box is a file. Each helper (an agent) gets one box at a time. If you want a new ability, you add a new box. You do not scribble inside someone else's box.

Two kinds of boxes:

  • Ability boxes = code. One file per ability: wings, legs, fire breath.
  • Instruction cards = data. One small file per kind of thing: a dragon, an elf, an element like iron, a star type. A new dragon-like creature is a new card, not a code change.

A dragon is not "a child of Reptile and Flyer". It is a thing that has wings, legs and fire breath. Mix and match, like Lego. The core of the program knows nothing about dragons or stars: it only knows what a brick is and keeps a list of bricks.

The same shape works for a whole universe (stars, planets, materials, creatures) and for an app (features, buttons, saving, input).

2. Why two kids must not write on the same paper

Somewhere there is usually a list of all the bricks. If every helper adds a line to that one paper, they crash into each other. The fix: nobody writes the list by hand. The computer builds the list by looking at the folders. Add a file, and the list grows by itself.

3. Stairs: climb only when you must

Most things stay on the bottom step. We climb one step only when a measured signal says so, never "just in case".

Step 0: plain filesOrdinary files. Small stuff stays here. Tiny scripts and one-off jobs use none of this.Climb to step 1 when: two helpers edited the same file in one round, or one file is over about 800 lines mixing several abilities.
Step 1: one file per abilityA core file holds the rules; each ability is its own file; no ability file edits another.Climb to step 2 when: a hand-written shared list has 2 or more helpers adding to it at once, or any conflict shows up in a round.
Step 2: list built by itselfThe list of bricks and cards is generated from the folders (a small build script, about 45 lines). Adding things = adding files only.Climb to step 3 when: there are very many kinds of things, or builds get too slow. The numbers for this are still guesses (see section 6).
Step 3: big machineryA proper "bag of parts" engine, kinds loaded from data, groups of abilities as separate packages.Measure the real project first: the thresholds are guesses.

Going back down is allowed: if a step shows 0 conflicts and fewer helpers, it may be simplified.

4. What we measured

Small tests on 2026-11-11 on one Mac. Real numbers, honest labels.

VERIFIEDAuto-built list: 0 conflicts. Two helpers each added an ability file plus a data file, merged, no conflicts, both abilities worked. Breaking the generator on purpose made the tests fail, so the tests do check it. A trap found: a shared test file would conflict, so each ability gets its own test file.
MEASUREDHand-written list vs generated list. With 2, 4 and 8 helpers adding at once: a list where everyone appends a line at the end conflicted in 100% of trials. A sorted list conflicted in 15%, 75% and 100% of trials. The generated list (files only): 0 conflicts at 2, 4 and 8.
REFUTEDThe linkme trick on web-assembly. It does not compile there (all 4 builds failed). It works natively only. Do not use it on wasm.
VERIFIEDThe inventory trick on web-assembly. Counted 3 of 3 bricks, and 0 with no bricks (control). Tested in node only.
VERIFIEDThe code-analysis tool sees the generated modules. The command-line analyzer passed normally, failed on a deliberately wrong import, and failed when build scripts were switched off. It only prints pass/fail, not messages.
MEASUREDSpeed. 2000 data cards plus 200 ability files built from scratch in 2.4 seconds; scanning the folders took 12 ms. With toy modules, so file count alone does not make builds slow. It does not tell us the real limit.
MIXEDOther languages. Zero-edit worked (0 conflicts, 3 behaviors) in Python, TypeScript on node, Go (same-package files, or a generated import file), Java (scan a classes folder), and C++ (file globbing). Not zero-edit, 1 conflict each: Java ServiceLoader (one shared services file) and Go blank-import lists. C++ code inside a static library was silently dropped by the linker (0 behaviors).
VERIFIEDOld projects (brownfield). Never rewrite everything. Add a scaffold beside the old code, plug the old code in through a thin adapter, then extract one thing per card. The extraction branches only add files; both merged with 0 conflicts and the old tests stayed green. But if two branches each delete their own line from the old shared list, that conflicts, so the owner deletes the old lines in one cleanup afterward. Tested on one tiny Rust crate with 3 kinds.

5. Old projects in one picture

Only what a task actually touches is moved, and only when the one-file-per-helper promise would otherwise break. Everything else stays old. Other languages for this part were not tested.
